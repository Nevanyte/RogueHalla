## 1. ID and outcome

While a Frost Wall stands, the server's bodies, swings and paths read the arena map with the wall's tiles set to LOW
(`TILE_LOW`). The Unity client's local walk mirror (`LocalMotion`, `Pathfinder`, `KeyboardSteer`) reads only the Welcome
map, so it walks through ice the server walks round: keyboard steering into a wall walks the sprite into the ice and
snaps it back (about 96 u, `LocalMotion.SnapDistance`) over and over; a click past a wall walks straight through while
the server detours. When this packet lands, the mirror plans, steers and re-plans on the same map the server does: the
Welcome map with every standing wall's tiles LOW, rebuilt only when the wall set changes. A wall that rises on the
predicted path re-plans the walk exactly as the server's `raise_wall` re-plans every blocked walk; a wall that falls
reopens its tiles for every later plan (the server does not re-plan on a fall, and neither does the mirror). A fighter
the rising wall lands on is set down by the server (a displacement); the mirror follows the server's correction and
pushes nothing itself.

- **From which tick.** `systems/abilities/effects.rs:265-372` `raise_wall`, run in the `abilities` phase

  `movement` (`schedule.rs:985-1010`). In the landing tick T: cells chosen; fighters overlapping the cells set down

  `pathfind.rs:464-473` `find_path_into`: the same A* as a Move order, with the fighter's own foot). An unreachable

- **To which tick.** `systems/status/mod.rs:92-137` `end_fields_with` (run by `status::expire` at the start of the

## Design (the seam)

- One overlay, owned by `LocalMotion`: a second `MapBlob` (the walk map) that is the current base map (Welcome, or the
  map `SetCollisionMap` supplies) with every standing wall's tiles set to `MapBlob.Low` when they are `MapBlob.Floor`
  (the C# `with_low`). With no wall the walk map IS the base map object (Freeze worlds and wall-less moments plan on
  exactly today's map, today's tables). Rebuilt only when the wall set changes (compare the `AreaKey`s of the `Kind ==
  Wall` rows against the held keys in a reused array: no allocation when nothing changed); a rebuild may allocate (new
  tiles copy or in-place rewrite plus the pathfinder's table rebuild), as the server's `sync` does.
- New public API (stubbed in the `stub:` commit, bodies are the implementer's):
  - `LocalMotion.SetWalls(IReadOnlyList<AreaView> fields)`: the caller hands it `Collections.Fields` after every State
    message. Non-wall rows are ignored. When a wall was added, and the remaining walk from the model position is blocked
    on the new walk map (`walk_blocked`: each remaining leg, `Pathfinder.SegmentClear(walkMap, from, p, 12.0)`, a 12 u
    disc, as the server), re-plan from the model position to the walk's last waypoint with the own `Foot`
    (`_pathfinder.FindPath(walkMap, ...)`); an empty result stops the walk. A wall removed re-plans nothing. Prediction
    suspended (gates locked) keeps the walls for when it resumes.
  - `LocalMotion.WalkMap` (`MapBlob`): the map the mirror plans on; `KeyboardSteer` callers pass it instead of the
    Welcome map.
  - `SetCollisionMap(map)` rebuilds the overlay over the new base with the walls held.
- Caller: `Session.cs` State branch (after `Collections.Apply`, beside the gate-lock handling, `Session.cs:461-470`)
  calls `Motion.SetWalls(Collections.Fields)`; `MatchClient.cs:478` passes `Session.Motion.WalkMap` (falling back to
  `Session.Map` when there is no Motion).
- The push: when a rising wall lands on the local fighter, the server sets it down and bumps `displace_seq`; the mirror's
  existing hard cut (`LocalMotion.cs:403`, `:427-446`: model to the server, walk dropped) follows it. No client-side push,
  no client gap: the gap is in the tiles the server sends.
- Re-plan origin under latency: the vectors are lockstep (zero delay), where the model at the State of tick T stands
  where the server stood at T-1, so "re-plan from the model position" is exactly the server's re-plan. Under real
  latency the model leads by the order delay and the re-plan origin differs by that lead; the ordinary reconciliation
  corrects it. Rewinding to the aligned pose was considered and left out (more code, not observable in the vectors).

## 11. Known traps

- Same-tick competitions: a Move applied on the wall's landing tick is planned on the map before the wall (inputs run
  before abilities) and then re-planned by `raise_wall` if blocked; a Move applied on the expiry tick is planned with
  the wall still up (vector `expires_mid_walk` pins both boundaries).
- The re-plan goal is the walk's LAST WAYPOINT (the snapped goal), not the clicked point.
- A wall that falls re-plans nothing: the detour is walked to its end.
- `SetWalls` is called with the same wall set many times (every State message): it must not re-plan or allocate then.
- The gap: tiles kept free round a fighter are simply absent from the wall's `Tiles`; nothing to compute client-side.
- The push: the hard cut (`displace_seq`) drops the predicted walk while the server walks on (the server re-plans the
  pushed fighter's walk, `displace.rs:45-58`); the mirror then trails the server by about one tick's walk until the walk
  ends. That is today's behaviour for every displacement and is pinned as "no snap, bounded lag, converges", not changed.
